# Proposed Haven frontend API contract

These routes and shapes are **proposals, not confirmed backend contracts**. Align them with the backend team's OpenAPI document. The UI uses `ApiAdapter`; paths are centralized in `src/services/api/endpoints.ts`, and Zod schemas in `src/types/models.ts` are the runtime and TypeScript source of truth. The base URL is an origin configured with `EXPO_PUBLIC_API_BASE_URL`.

## Transport and authentication

HTTPS and JSON (`Accept: application/json`, `Content-Type: application/json` for bodies). All responses below are direct JSON values, not `{ data: ... }` envelopes. Use ISO 8601 UTC date strings, e.g. `2026-11-07T19:00:00.000Z`. All IDs and cursors are strings. Numbers are JSON numbers, not strings. Optional fields may be omitted; nullable fields must be explicit `null` where specified by the schemas.

Use the backend team's authentication mechanism. `session.setToken` accepts a token from that flow, isolates storage, and adds `Authorization: Bearer <token>` when available. No token or production credentials are generated by this app. The backend must scope household, plans, requests, reports, and changes to the authenticated household and enforce authorization on every detail endpoint. A demo session has no authentication and runs entirely through MockAdapter.

POST assistance/report endpoints receive `Idempotency-Key`, matching `idempotencyKey` in their JSON body. Repeating a key must return the same acknowledged result without duplicate side effects, including after a timeout. The app does not automatically retry mutations. Use 200/201 with the full created record, not 202/204 with an empty body. Profile updates return the complete household. Before adding additional account sessions, integrate logout/cache deletion.

## Routes

- `POST /api/v1/households`: HouseholdInput → Household.
- `GET /api/v1/households/me`: Household or `null` when onboarding is incomplete (200).
- `PUT /api/v1/households/me`: HouseholdInput → Household.
- `GET /api/v1/alerts`: DisasterAlert[].
- `GET /api/v1/plans/current`: ResponsePlan or `null` when no plan is available.
- `GET /api/v1/plans/history`: ResponsePlan[], newest first, including current version.
- `POST /api/v1/assistance-requests`: AssistanceInput → AssistanceRequest.
- `GET /api/v1/assistance-requests`: AssistanceRequest[], newest first.
- `GET /api/v1/assistance-requests/{id}`: AssistanceRequest. IDs are URL encoded by the client.
- `POST /api/v1/situation-reports`: ReportInput → SituationReport.
- `GET /api/v1/situation-reports`: SituationReport[], newest first.
- `GET /api/v1/updates`: Update[], sorted by timestamp descending in the UI.
- `GET /api/v1/changes?after={cursor}&timeout=20`: Changes. Path configurable with `EXPO_PUBLIC_CHANGES_PATH`; set `disabled` to use manual refresh only.

## Household example

POST/PUT body (counts are integers; adults 1–30, children/pets 0–30, seats 0–50):

```json
{
  "name": "The Morgan household",
  "adults": 2,
  "children": 2,
  "pets": 1,
  "petTypes": "Dog",
  "needs": ["Wheelchair accessibility"],
  "otherNeeds": "",
  "hasCar": true,
  "canDrive": true,
  "seats": 4,
  "needsTransport": false,
  "needsShelter": true,
  "needsFood": true,
  "location": { "label": "Wilmington, NC" }
}
```

Household response is the body above plus `"id": "household-123"` and `"updatedAt": "2026-11-07T19:00:00.000Z"`. Location may include optional numeric `latitude` (-90–90) and `longitude` (-180–180), only after permission. `otherNeeds` is at most 300 characters. Do not require diagnoses or medication histories. Known needs: Wheelchair accessibility, Limited mobility, Essential medication, Refrigerated medication, Electric medical equipment, Accessible transportation. The model tolerates additional short support labels.

## Sources and assignments

All critical information must carry a source. A `Source` is:

```json
{ "name": "County Emergency Management", "kind": "government", "verified": true, "url": "https://authority.example/updates" }
```

`kind`: `government | organization | unverified`; `verified`: boolean; `url`: optional absolute URL. Verification must be provided by the service, not inferred by the client.

An Assignment is:

```json
{
  "name": "Shelter name supplied by the backend",
  "description": "Accessible household spaces; confirm availability with provider.",
  "address": "Address supplied by the backend",
  "organization": "Relief partner",
  "status": "pending",
  "source": { "name": "Relief partner", "kind": "organization", "verified": true }
}
```

`address` is optional. Resource statuses: `confirmed | pending | unverified | unavailable | cancelled`. Pending must never be treated as confirmation. Availability is not inferred from a cached record.

## Response plan example

```json
{
  "id": "plan-123", "householdId": "household-123", "disasterId": "event-1", "disasterType": "Hurricane",
  "version": 2, "status": "active",
  "createdAt": "2026-11-07T18:00:00.000Z", "updatedAt": "2026-11-07T19:00:00.000Z",
  "summary": "Review your assigned support and current official information.",
  "changes": ["Transportation assignment updated by relief partner."],
  "officialInstructions": [{ "text": "Instructions provided by the issuing authority.", "source": { "name": "County Emergency Management", "kind": "government", "verified": true } }],
  "actionSteps": [{ "id": "task-1", "title": "Review your household essentials", "detail": "Preparation task supplied by the backend.", "personalTask": true }],
  "shelterAssignment": null,
  "transportationAssignment": null,
  "additionalResources": [], "unmetNeeds": ["Accessible transportation"],
  "sources": [{ "name": "County Emergency Management", "kind": "government", "verified": true }]
}
```

Assignments use the full Assignment shape or `null`. `status`: `active | pending | superseded`. Versions are monotonically increasing positive integers per plan. Return the newest version from current; retain older versions in history. Provide explicit `changes` descriptions so the client can show what changed without generating instructions. Emit a `plan` event for revisions. Personal checklist state stays on device and does not mutate official steps or allocations.

## Assistance example

```json
{
  "category": "transportation", "people": 3,
  "requirements": ["Wheelchair accessibility"],
  "description": "Accessible vehicle needed.",
  "location": { "label": "Wilmington, NC" },
  "idempotencyKey": "6ac760f3-1d23-4d41-811b-1917d1f8d2af"
}
```

`location` is optional and requires explicit sharing in the request form. `people`: integer 1–60. `description`: at most 1,000 characters. Categories: `transportation | shelter | food_water | medical_supplies | accessibility | other`.

Response is the input plus:

```json
{
  "id": "request-123", "status": "submitted", "organization": null,
  "createdAt": "2026-11-07T19:00:00.000Z", "updatedAt": "2026-11-07T19:00:00.000Z",
  "timeline": [{ "status": "submitted", "timestamp": "2026-11-07T19:00:00.000Z", "message": "Received by coordination service." }]
}
```

Statuses: `submitted | under_review | matched | accepted | in_progress | fulfilled | unable_to_fulfill | cancelled`. `organization` is a string or null. Statuses and timeline entries must come from the backend. HTTP success alone is not acceptance by an organization.

## Reports example

```json
{ "kind": "I am safe", "description": "Staying with relatives.", "idempotencyKey": "report-key-123" }
```

`kind` must be one of: `I am safe`, `I need assistance`, `My transportation is unavailable`, `My assigned resource is inaccessible`, `My household circumstances have changed`, `I want to report an issue`. Description is up to 1,000 characters. Response is the input plus:

```json
{ "id": "report-123", "createdAt": "2026-11-07T19:00:00.000Z", "acknowledgment": null }
```

Receipt means the coordination service accepted the report. `acknowledgment` is a separate string or null for an organization acknowledgment. Never imply direct government delivery without a verified integration. Offline drafts are local only and require explicit review and submission.

## Alerts and updates examples

```json
{
  "id": "alert-123", "disasterType": "Hurricane", "title": "Official warning title", "message": "Authority-provided message.",
  "area": "Affected geographic area", "severity": "warning",
  "source": { "name": "County Emergency Management", "kind": "government", "verified": true },
  "updatedAt": "2026-11-07T19:00:00.000Z"
}
```

Severity: `warning | watch | info`.

```json
{
  "id": "update-123", "category": "plan", "title": "Your plan was updated", "message": "The team updated your arrangements.",
  "source": { "name": "Relief partner", "kind": "organization", "verified": true },
  "timestamp": "2026-11-07T19:00:00.000Z", "planId": "plan-123"
}
```

Update categories: `warning | government | organization | request | resource | plan`. `planId` and `requestId` are optional links.

## Changes, reconnects, and errors

```json
{ "cursor": "opaque-cursor-42", "events": [{ "id": "unique-event-42", "entity": "plan" }] }
```

Entities: `household | plan | alerts | requests | updates | reports`. IDs remain stable when an event is replayed. A cursor is an opaque string representing the acknowledged stream position. Wait up to 20 seconds for events; empty results must still be valid JSON with the current cursor. Return the next cursor even for an empty batch. The app keeps a cursor for the foreground connection; on reconnect it refreshes all active data then starts a new change session. Ensure no event gap between initial fetch and stream initialization: an omitted cursor should replay retained recent changes or return an appropriate starting snapshot. Replayed events are safe and deduplicated. If cursor expiry is introduced, coordinate its status/reset semantics with the client.

404/405/501 on the changes endpoint means unsupported: the client stops polling and offers manual refresh. Other network/service failures retry with exponential backoff. Each request has a 15-second timeout; the 20-second poll uses 25 seconds. Requests abort when backgrounded or offline.

Errors should use an appropriate non-2xx HTTP status and a proposed body:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Invalid household input", "requestId": "trace-123", "fields": { "adults": "At least one adult is required" } } }
```

Use 400/422 for validation, 401 for expired/missing credentials, 403 for forbidden records, 404 for missing detail records, 409 for a conflicting idempotency key, 429 for rate limits, 503 for unavailable service. The current client intentionally displays safe generic errors by HTTP status, avoiding untrusted/sensitive backend text. It runtime-validates all successful responses and rejects malformed payloads instead of presenting them as current information. If adopting server error codes or Retry-After, adapt the shared HTTP client in one place.
